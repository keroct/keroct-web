# KEROCT造船所 Webサイト構想メモ

> **ステータス:** アイデア段階 / KEROCTメンバー相談待ち\
> **更新日:** 2026年10月6日（問い合わせ導線をWebチャット / Shared
> Inboxへ変更）\
> **用途:**
> 後から構想を再現するためのメモ。必要なら、そのまま企画共有用のたたき台として使う。

## 1. 企画の出発点

現在のKEROCT造船所は、Discord上にデザイン・イラストの料金表や注意事項が整理されており、相談・制作進行にもDiscordを利用している。

Discordは、依頼後のヒアリング、参考資料の共有、ラフ確認、修正、納品など、**密なやり取りをする場所としては非常に相性がいい**。通話や複数スタッフの参加、BOTによる補助、権限管理も強みであり、案件化後の制作進行とスタッフ側運営の基盤として活用する。

一方、まだ依頼するか決めていない人にとっては、最初からDiscordへ参加すること自体が心理的なハードルになり得る。

そこでDiscordを置き換えるのではなく、**作品・料金・作り手を安心して見られ、そのまま初回問い合わせまで進める公開Webサイトを用意する**。初回問い合わせでDiscordサーバーへの参加を必須にせず、Webサイトに埋め込んだWebチャットからそのまま相談できるようにする。

## 2. 解決したい心理的摩擦

Discordは「相談する場所」には強いが「検討する場所」には向きづらい。

中の様子が見えないまま「人のいる場所に入る」感覚があり、カードゲームショップの対戦台へ入っていくときのような心理的参入障壁になり得る。作品を見たい、料金を知りたい、まず質問したいという段階では、この参加の負担が問い合わせをためらう理由になる。

-   Discordを入口にすると、まだ依頼すると決めていない段階で、閉じたコミュニティへ参加する必要が生じる
-   「ちょっと見るだけ」がしづらく、店に入るような心理的負担がある
-   最新メッセージ側から見る構造なので、運営側が意図した順番で説明を読ませにくい
-   チャンネル分けは情報整理には有効だが、Webページのような上から下への体験設計は難しい
-   画像を文章の任意位置・大きさ・レイアウトで配置しづらく、ポートフォリオを主役にしにくい
-   視覚的に「文字が並んでいる」状態になりやすい
-   作品や作り手が十分見えないままでは、「何が出来上がるか分からない」という不安が残る

**商品や価格が原因ではなく、商品を十分検討する前に離脱する可能性がある。**

## 3. 媒体ごとの役割

リアル店舗にたとえる。

### X = 街中の大きな広告看板

強い制作サンプルを4枚程度掲載し、それぞれに商品名と基本料金を簡潔に表示する。

例：

-   LOGO DESIGN --- ¥6,000〜
-   STREAM DESIGN --- ¥10,000
-   ILLUSTRATION --- ¥8,000〜
-   TRADING CARD --- ¥10,000

本文では「制作例・料金・ご依頼についてはこちら」とWebサイトへ誘導する。

Xでは説明より、

-   「この作品いい」
-   「これ依頼できるの？」
-   「この値段なら見てみたい」

という最初の興味を作る。

### Webサイト = 店頭のショーケース / 写真付きメニュー

誰にも話しかけられず、自分のペースで、

1.  欲しいものを見つける
2.  作例を見る
3.  作り手を知る
4.  値段を確認する
5.  依頼方法を理解する
6.  「ここなら頼みたい」と思う

ところまで進める場所。

問い合わせCTAからWebチャットを開き、サイトを離れずにKEROCTへ直接相談できるようにする。

### Webチャット / Shared Inbox = 初回問い合わせ・相談窓口

Webサイトにtawk.toのチャットウィジェットを埋め込み、依頼者はサイト上からKEROCTへ直接メッセージを送れるようにする。KEROCT側はShared
Inboxで依頼者ごとの会話をまとめて確認し、スタッフ複数人でそのまま返信・対応する。

スタッフがオンラインならリアルタイムチャットとして対応し、不在時もメッセージを受け付けられる構成にする。問い合わせのためだけにGoogleフォーム、Apps
Script、メール返信を経由させない。

### Discord = 必要に応じた制作進行・通話 / スタッフの作業場

Webチャットでの相談後、通話や制作進行などDiscordを使う利点がある案件では、必要に応じて依頼者を専用Discordチャンネルまたは専用サーバーへ案内する。すべての問い合わせをDiscordへ移すことは前提にしない。

**Xで見つけてもらう。Webで好きになってもらう。その場でチャットしてもらう。制作では、必要に応じてDiscordを使う。**

## 4. トップページは作品から始める

最初から長い理念説明をするのではなく、**まず制作物を見せる**。

訪問者が最初に知りたいのは「KEROCTとは何者か」より、

> **ここに頼むと、どんなものが手に入るのか？**

### 大まかな流れ

1.  HERO --- KEROCT造船所の世界観
2.  SHOWCASE --- 強い制作例を大きく見せる
3.  制作カテゴリ / メニューへの入口
4.  CREATORSへの入口
5.  料金・依頼方法への入口
6.  「制作について相談する」CTA → Webチャット

ABOUTは必要だが、必ずしも最上部に置く必要はない。

## 5. SHOWCASEは「食品サンプル」

料金だけ先に見せると、判断が「高い / 安い」になりやすい。

しかし、

1.  欲しい作品を見る
2.  「これいい」と思う
3.  その後に料金を見る

という順番なら、

> 「これがこの金額で頼めるの？」

という判断になり得る。

SHOWCASEは単なる実績一覧ではなく、**中華料理店の食品サンプルのように「これが欲しい」を発生させる場所**として考える。

## 6. 生産者の顔を見せる

AIで「それっぽい制作物」を安価・高速に作れるほど、人へ依頼する理由は、

> 「作れる人だから」

だけでなく、

> **「この人に作ってほしいから」**

へ寄っていく。

KEROCTというブランドだけを見せて、制作する人間を隠さない。

## 7. CREATORSと個人ページ

グローバルナビに `CREATORS` を用意する。

現在は3人だが、3人を一枚の固定紹介ページに閉じ込めず、**各クリエイターに独立したページを持たせる**。

例：

-   `/creators/creator-a/`
-   `/creators/creator-b/`
-   `/creators/creator-c/`

個人ページには、名前、アイコン・立ち絵、本人からの一言、得意分野、作風、代表作、その他の制作実績、SNS・活動先、必要に応じた依頼導線を置く。

「本人からの一言」は、整いすぎた企業コピーより本人の言葉や文章の癖をある程度残す。目的は、**作品の作者から「人」に変えること**。

## 8. KEROCTと個人クリエイターの関係

KEROCTが一つの会社として案件を受注するなら一体化した企業サイトも自然だが、**個人事業主の集まり**として活動するのであれば、各個人の存在を独立して見せる方が実態に合う。

イメージは、

-   **KEROCT造船所：複数の職人が一緒に構えている店 / 造船所**
-   **各クリエイター：そこで仕事をする独立した職人**

KEROCTブランドで集客しながら、個々のクリエイターが指名される余地も残す。

## 9. 将来の人数増加を前提にする

現在の3人だけを前提にサイト構造を固定しない。

将来的に4人、6人、10人と増えても、

-   CREATORSへ追加
-   個人ページを追加
-   WORKSと作者を紐付ける

だけで拡張できる構造にする。

人数が増えれば、ILLUSTRATION / LOGO / STREAM DESIGN / MOVIE
など、得意分野から探す仕組みも検討できる。

### 各ページの見せ方は統一しすぎない

共通化するのはヘッダー、ナビ、基本デザイン、フッターなど「同じKEROCTサイトにいる」と分かる骨格。

中身は作品に合わせて変えてよい。

-   イラスト中心 → 大判作品を主役にする
-   ロゴ・グラフィック中心 → 制作事例単位で見せる
-   映像中心 → 動画中心にする

**共通テンプレートに人を押し込むのではなく、共通の額縁を用意する。**

## 10. 料金体系の考え方

現状の料金表を見る限り、料金はクリエイターごとではなく**KEROCT共通の基本料金**に見える。

その場合、

### KEROCT側が持つ情報

-   制作メニュー
-   基本料金
-   セット料金
-   オプション
-   納期
-   修正条件
-   依頼フロー
-   受付

### クリエイター側が持つ情報

-   作風
-   得意分野
-   作品
-   本人コメント
-   SNS
-   「この人に頼みたい」と思える情報

個人ページごとに料金表を複製する必要はない。

## 11. 問い合わせ受付と制作進行

初回問い合わせはWebサイト上のCTAからWebチャットを開く。Discordサーバーへの参加やGoogleフォームへの移動は必須にしない。

### 受付から制作進行まで

1.  依頼者がWebサイト上のチャットから問い合わせを送信する
2.  問い合わせがKEROCTのShared Inboxに入り、スタッフが確認する
3.  スタッフがShared Inboxからそのまま返信し、依頼者と会話する
4.  相談を通じて依頼内容・条件を確認し、案件化する
5.  Webチャットのままで十分な場合は、そのままやり取りを継続する
6.  通話や制作進行などDiscordを使う利点がある場合は、必要に応じて専用Discordチャンネル
    / サーバーへ案内する

Webチャットは単なる通知手段ではなく、依頼者とKEROCTが双方向に会話する受付・相談窓口として扱う。KEROCT側ではShared
Inboxに依頼者ごとの会話を集約し、複数スタッフで対応する。Discordは問い合わせの必須入口ではなく、必要な案件で制作進行・通話・スタッフ側運営を支える基盤とする。

### Discordへ案内するときの説明

案内時には、その場所で何をするか、誰が参加するか、どのチャンネルを使うかを伝える。最初は設定ではなく、**歓迎と説明**から始める。

例：

> **KEROCT造船所へようこそ！**\
> こちらは、ご依頼の打ち合わせと制作進行に使う場所です。\
> ご案内した専用チャンネルで、参考資料の共有やラフの確認を進めます。必要に応じて通話も行えます。\
> 担当スタッフがご案内しますので、ご不明な点はお気軽にお知らせください。

ロール選択などの操作が必要な場合は、操作の目的と結果を説明する。たとえば「リアクションを押してください」だけでなく、**「リアクションを押すと、制作進行用のチャンネルが表示されます」**と伝える。

## 13. サイトの役割を一言で

> **KEROCT造船所の外に、誰でも安心して覗けるショールームを作る。**

Discordを捨てるのではない。

Webが前段階の「見る・知る・選ぶ・安心する」を担当し、Webチャットがそのまま初回問い合わせと相談を受け付ける。KEROCT側はShared
Inboxで会話を集約して複数スタッフで対応する。Discordは、通話や複数スタッフの参加、BOT・権限管理の強みが必要な案件で、制作進行とスタッフ側運営を担当する。

### サイト運用の前提

WebサイトはGitHub
Pagesで運用し、**運営費ゼロを前提**とする。問い合わせ受付にはtawk.toのWebチャット
/ Shared
Inboxを利用し、KEROCT側で問い合わせ用サーバーを運用しない構成で進める。無料プランの範囲で運用し、将来必要になった場合のみ有料機能を検討する。

    オフライン時の案内文

-   問い合わせ時に取得する名前・メールアドレス等の項目
-   通知設定・営業時間 / オンライン運用の方針
-   画像・ファイル共有を含むWebチャット内での対応範囲

-   KEROCT側で担当者を決めるケースはあるか
-   問い合わせから制作開始までの実際の流れ
-   掲載可能な納期・修正条件
-   将来メンバー追加時の運用方針

## 15. 現在地

現時点では**サイト制作は正式決定していない**。KEROCT側はメンバー内で相談予定。

2026年10月5日の会話でGoogleフォーム + Google Apps
Scriptによる問い合わせ導線を検討したが、フォーム送信後に依頼者へ返信・継続会話する場所が分断される問題が判明した。

2026年10月6日の検討で、問い合わせ窓口をWebチャット / Shared
Inboxへ変更する方針とした。

-   GitHub Pagesでサイトを運用し、運営費ゼロを前提にする
-   初回問い合わせはWebサイトに埋め込んだtawk.toのWebチャットから受け付ける
-   KEROCT側はShared
    Inboxで依頼者ごとの会話を集約し、スタッフ3人で確認・返信する
-   Googleフォーム + Google Apps Script +
    Discord通知を問い合わせの基本導線にはしない
-   依頼者に初回問い合わせのためのDiscord参加を必須にしない
-   Discordは、通話や制作進行など利点がある場合に必要に応じて利用する
-   Webチャット用の自前サーバーは持たず、tawk.toの無料プランを前提に検証する

料金表など既存情報だけを元にした静的HTMLの簡易プロトタイプは作成済み。これは完成デザインではなく、「この程度なら短時間で形にできる」という確認用の叩き台。

正式に進める場合は、この構想を元に素材を受け取り、情報設計・デザイン・実装を詰める。
